# Развёртывание бэктестера образом (U8)

Это путь на замену `up.sh`. Разница не в удобстве: `up.sh` поднимает стенд из
каталога с исходниками, и что именно там за код — установить нельзя.

## Почему это понадобилось

Проверка staging 2026-07-30: каталог развёртывания `/home/deploy/projects/backtester`
**не является git-репозиторием** — скопированное дерево. Ни коммита, ни ветки, ни
digest'а. Сервис работал 3 дня 22 часа, и сказать, какая ревизия исполняется, было
невозможно.

Safe-deployment framework требует пиннить единицу развёртывания по digest. Пиннить
было нечего: развёрнуто не то, что публикуется.

Тем же выездом подтверждено, что **образ на VPS работает**: задание прошло полный
путь до `completed` под Node 24. То есть U8 упирался не в работоспособность образа.

Свидетельство: control-center
`docs/operations/evidence/2026-07-30-backtester-staging-image-validation.md`.

## Как развернуть

```bash
# 1. Узнать digest публикуемого образа (тег latest ставится на каждый пуш в main)
docker pull ghcr.io/trdlabs/backtester:latest
docker inspect --format '{{index .RepoDigests 0}}' ghcr.io/trdlabs/backtester:latest

# 2. Записать ИМЕННО digest, а не тег
export BACKTESTER_IMAGE='ghcr.io/trdlabs/backtester@sha256:<digest>'

# 3. Env — тот же контракт, что у up.sh
cp backtester.env.example backtester.env && $EDITOR backtester.env

# 4. Поднять
docker compose up -d

# 5. Убедиться, что оба сервиса здоровы (не «запущены», а именно healthy)
docker compose ps
```

Теги, которые публикует CI: `latest` и `sha-<короткий коммит>`. Тега `main`
**не существует** — попытка выкачать его даёт `not found`, который легко
спутать с отказом в правах (тот выглядит как `denied`).

## Почему digest, а не тег

`latest` — движущаяся ссылка. Два развёртывания «одного и того же» дадут разный
код, и откатиться будет некуда. Digest неподвижен; он же записывается в журнал
развёртываний.

## Почему два сервиса из одного образа

У API и воркера разная природа нагрузки. API обязан отвечать быстро; воркер
занимает ядро барным циклом на десятки секунд (измерено: 460 мкс на
бар-вычисление на реальных данных, то есть 12 тысяч баров это ~6 секунд чистого
счёта). В одном процессе воркер отнимал бы у API время, поэтому API поднимается
с `BACKTESTER_AUTO_WORKER=false`, а воркер идёт отдельной точкой входа.

Число воркеров при этом меняется, не трогая API:

```bash
docker compose up -d --scale worker=2
```

**Осторожно со `--scale`:** барный цикл упирается в счёт, и воркеров больше,
чем ядер, выделенных сервису, не ускоряют, а замедляют — процессор тратится на
переключения. `WORKER_CONCURRENCY` внутри каждого воркера умножается на их
число.

## Про docker-сокет: его здесь нет намеренно

Compose **не монтирует** `/var/run/docker.sock`.

С `BACKTESTER_SANDBOX_BACKEND=isolate` недоверенный код исполняется в изоляте
внутри процесса, и сокет не нужен вовсе. Голый сокет ≈ root на хосте (аудит 17,
SBX-2), поэтому не заводить его правильнее, чем заводить и обносить прокси.

Для docker-бэкенда песочницы потребуется отдельная надстройка с socket-proxy
(allowlist на create/start/kill/rm/inspect). Она сюда намеренно не встроена,
чтобы её нельзя было включить по невнимательности.

## Сеть: соседние сервисы, опубликованные на 127.0.0.1, из контейнера НЕ видны

Это главная ловушка развёртывания, и она сработала дважды подряд при переводе
staging (2026-07-30).

`backtester-pg` публикует порт как `127.0.0.1:15533->5432`, `mock-platform-t2` —
как `127.0.0.1:8890->8839`. Публикация на петлю означает, что порт слушается
**только на loopback хоста**. Из контейнера адрес `host.docker.internal`
разрешается в адрес docker-шлюза (`172.17.0.1`), и там этого порта нет:

```
Error: connect ECONNREFUSED 172.17.0.1:15533
```

Лечится не адресом, а сетью: соседний контейнер подключается к сети проекта, и
обращение идёт **по имени контейнера и ВНУТРЕННЕМУ порту** — не по
опубликованному.

```bash
# один раз после первого `docker compose up -d` (сеть создаёт compose)
docker network connect backtester_default backtester-pg
docker network connect backtester_default mock-platform-t2
```

и в `backtester.env`:

```
DATABASE_URL=postgres://<...>@backtester-pg:5432/backtester      # 5432, не 15533
BACKTESTER_MOCK_PLATFORM_URL=http://mock-platform-t2:8839        # 8839, не 8890
```

**Сеть должен создать compose, а не человек.** Созданную вручную он не возьмёт —
у неё нет его меток, и он остановится с `network ... has incorrect label`.
Порядок: `up -d` (compose создаёт сеть) → `network connect` соседей → сервисы
поднимутся сами, потому что перезапускаются по `restart: unless-stopped`.

## Перенос env с пути `up.sh` — что обязательно переписать

Файл `backtester.env` от `up.sh` **нельзя брать как есть**: он написан для
процессов на хосте.

| что | было | должно стать |
| --- | --- | --- |
| адрес БД | `@127.0.0.1:15533/` | `@backtester-pg:5432/` |
| mock-platform | `http://127.0.0.1:8890` | `http://mock-platform-t2:8839` |
| каталоги данных | пути хоста | `/data/artifacts`, `/data/bundles` |
| привязка API | `127.0.0.1` | `0.0.0.0` (наружу выводит compose) |

Отдельно про `DATABASE_URL`: в нём адрес стоит **после `@`**, а не после `://`,
поэтому замена по шаблону «после схемы» его не тронет. Ошибиться здесь легко, а
проявится это только при старте — `ECONNREFUSED` из контейнера.

## Преемственность артефактов при замене работающего стенда

Основной файл использует именованные тома — верный дефолт для чистой установки.
Но когда стенд заменяется **на работающем месте**, строки в базе ссылаются на уже
записанные артефакты. Тогда рядом кладётся `docker-compose.override.yml`,
привязывающий прежние каталоги хоста:

```yaml
services:
  api:
    volumes:
      - /home/deploy/bt-data-staging/artifacts:/data/artifacts
      - /home/deploy/bt-data-staging/bundles:/data/bundles
  worker:
    volumes:
      - /home/deploy/bt-data-staging/artifacts:/data/artifacts
      - /home/deploy/bt-data-staging/bundles:/data/bundles
```

Надстройка машинно-зависимая и в репозиторий не коммитится.

## Чего этот файл пока не делает

- **не заменяет `up.sh` в репозитории** — скрипт остаётся путём отката;
- **не описывает Postgres** — база уже развёрнута (`backtester-pg`), и подмешивать
  её сюда значило бы завести вторую точку истины о том, где живут данные;
- **не настраивает мониторинг** — стенд отдаёт `/health`, `/healthz`, `/readyz`,
  `/statsz`; подключение к наблюдению идёт своим порядком.
