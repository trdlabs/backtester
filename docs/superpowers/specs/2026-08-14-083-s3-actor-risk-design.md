# 083 S3 — actor-семантика `DEFAULT_RISK`: проектирование до реализации

**Дата:** 2026-08-14 · **Срез:** 083 S3, подсрез «риск-контур» · **Статус:** design принят владельцем
2026-08-14; реализации нет

Предмет: как настоящий зарегистрированный профиль `default_risk@1.0.0` применяется в event-driven
пути. Требование владельца — сопоставить **каждое** поле профиля с `ActorCommand` /
`ActorEngineState`, назвать место clamp/reject **внутри** атомарного batch, зафиксировать форму
`riskDecisions` и негативные гейты без частичных эффектов.

Дизайн отвечает и на вопрос, которого в задании не было, но без которого оно не решается: **часть
полей профиля не имеет носителя в actor-языке**. Решения по ним приняты владельцем и записаны в §8;
итог сведён в **applicability matrix** (§4), и она — обязательная часть контракта среза: путь
**не заявляет полной поддержки** полей профиля.

---

## 1. Почему это не «прокинуть RiskEngine в раннер»

Профиль и актор говорят на разных языках, и различие не косметическое.

| | legacy барный путь | actor-путь |
| --- | --- | --- |
| что производит стратегия | `StrategyDecision` — `enter` / `exit` / `add_to_position` / `update_protection` / `idle` | `ActorCommand[]` — `place` / `cancel` / `timer.set` / `timer.cancel` / `annotate` |
| что это по смыслу | **намерение о позиции** | **заявка в книге** |
| кто назначает размер | риск: `RiskOutcome.notional` | автор: `place.qtyUsd` |
| где живёт защита | `stop` / `take` как **доли**, клампятся риском | отдельная `stop_market`-заявка с **абсолютной ценой** |
| точка оценки | одно решение на бар | батч команд на каждое доставленное событие |

`RiskEngine.evaluate(decision, barIndex, ctx)` принимает `StrategyDecision`. Актор его не
производит. Значит между командой и риском обязан встать перевод — и вопрос дизайна не «куда
воткнуть вызов», а **насколько этот перевод тотален**. Он не тотален, и это главный результат
разведки.

## 2. Канонические источники (сверено с установленным `@trdlabs/engine@0.17.0`)

`DEFAULT_RISK` целиком (`src/engine/profiles.ts`):

```ts
{
  id: 'default_risk', version: '1.0.0',
  maxConcurrentPositions: 1,
  exposureLimits: { maxPositionNotionalPct: 1.0 },
  allowedSides: ['long', 'short'],
  stopBounds: { min: 0.001, max: 0.5 },
  takeBounds: { min: 0.001, max: 1.0 },
}
```

`dcaLimits` / `scaleInLimits` **не объявлены** — по документированному правилу профиля это значит,
что `add_to_position` запрещён (`dca_not_permitted` / `scale_in_not_permitted`).

Адаптер `src/engine/risk.ts` добавляет производное поле: `sizing: { kind: 'equity_pct', pct:
exposure.maxPositionNotionalPct }` — то есть **потолок экспозиции служит и авторитетом сайзинга**,
а база — mark-to-market equity (SSOT decision 3).

Формы, которые нельзя изобретать заново:

- `RiskOutcome` — `action: 'accept' | 'clamp' | 'reject'`, плюс `notional` / `stop` / `take` /
  `closeFraction` / `record`;
- `RiskDecision` — `{ barIndex, decisionKind, action, reason, clamped?: RiskClamp[] }`;
  `RiskClamp` — `{ field, from, to }`;
- `RiskContext` — `{ equity, openPositions, position?: { size, entryPrice, addCount } }`;
- `Validation` — **`{ ok: true } | { ok: false, reason }` и больше ничего**;
- `BatchCore<C,S>` — `validate(command, state)` и `apply(command, state)`, обе чистые от одной и
  той же пары аргументов; `apply` обязана быть тотальной (вернуть состояние либо бросить).

## 3. Пополевое сопоставление

| поле профиля | значение | носитель в actor-мире | вердикт |
| --- | --- | --- | --- |
| `id` / `version` | `default_risk@1.0.0` | — | идентичность; едет в `RiskDecision` и в inputs прогона |
| `maxConcurrentPositions` | `1` | `state.ledger.qty !== 0` | **применяется при одном акторе**. Прогон с несколькими акторами под profile-объявленным portfolio-wide лимитом **отвергается до создания акторов** (§8.3): актор соседа во время `validate` не видит, а per-actor трактовка запрещена владельцем |
| `exposureLimits.maxPositionNotionalPct` | `1.0` | `place.qtyUsd` против equity | **применяется** клампом; база — текущая realized equity при flat, mark-цена не требуется (§5) |
| `allowedSides` | `['long','short']` | `place.side` + знак `state.ledger.qty` | **применяется только на открытии**: сравнивается **результирующая сторона позиции**, а не сторона заявки. `sell` при длинной позиции — выход, а не short. Выходом считается только `reduceOnly` (§3.1) |
| `stopBounds` | `{0.001, 0.5}` | **нет носителя** | **не применяется** (§8.2). У актора нет stop-хинта; `stop_market` несёт абсолютную цену, а bounds — доли, и базовой цены нет, пока позиция не открыта |
| `takeBounds` | `{0.001, 1.0}` | **нет носителя** | **не применяется** (§8.2) |
| производное `sizing: equity_pct 1.0` | | `place.qtyUsd` | **роль риска меняется**: в legacy он размер *назначает*, здесь может только *клампить* объявленный автором. Кламп применяется **только к открытию**: урезать выход значило бы запереть капитал в активе, из которого нет выхода |
| `dcaLimits` / `scaleInLimits` | отсутствуют | `intentOf(ledger, side) === 'add'` | **любое увеличение открытой позиции запрещено** (§8.1). Режимы `dca` / `scale_in` не различаются и из косвенных признаков не выводятся |

Что из этого следует практически: под `DEFAULT_RISK` actor-путь может **открыть** позицию (flat →
nonzero) и **сокращать/закрывать** её. **Увеличивать открытую позицию не может.** Это и есть
содержательный смысл профиля, и именно он должен стать позитивным доказательством риск-среза.

### 3.1 Противоположная сторона ≠ закрытие (найдено ревью владельца)

Классификация по знаку («заявка смотрит против позиции ⇒ это выход») **не учитывает размер**.
Заявка на нотионал больше позиции пересекает ноль: движок закрывает старую экспозицию и остатком
открывает противоположную (`applyFill`, случай 3 — флип). Под видом выхода открывалась бы новая
позиция — **мимо `allowedSides`, мимо счётчика и мимо потолка**, потому что все три проверяются
только на ветке открытия.

Проверить размер на месте и «разрешить, если не пересечёт» **нельзя**: нотионал переводится в
базовый размер ценой ИСПОЛНЕНИЯ, которой в момент подачи не существует — её не будет до матча и
сдвига на проскальзывание. Любая арифметика здесь была бы оценкой, выданной за факт.

**Решение (S3):** выходом считается **только `reduceOnly`** — у неё пересечение нуля невозможно по
построению (движок клампит её знаковым остатком и отменяет, если сокращать нечего). Противоположная
non-reduceOnly при открытой позиции отвергается атомарно: ни заявки, ни филла, ни движения ledger.

**Следствие, которое надо знать:** одношаговый переворот позиции стал невыразим. Переворот
выражается двумя шагами — закрыть `reduceOnly`, затем открыть в другую сторону; второй шаг проходит
все проверки открытия, как и должен.

### 3.2 Проверки на подаче недостаточно: обход через время

Правило §3.1 закрывает момент подачи. Заявка, законно принятая при flat, **стоит в книге** и ждёт
свою цену; пока она ждёт, позицию открывает другая заявка — и к моменту срабатывания та же самая
заявка означает уже другое:

- смотрит **в сторону** появившейся позиции ⇒ наращивает её (профиль без add-лимитов это запрещает);
- смотрит **против** и не помечена `reduceOnly` ⇒ может пересечь ноль и открыть противоположную.

В обоих случаях правило обходится **через время**: на подаче оно выполнялось, на исполнении уже нет,
а второй проверки не было.

**Решение:** re-валидация в момент исполнения, **до `executeFill`**. Non-reduceOnly resting order
при non-flat снимается атомарно: филла нет, ledger не двигается, заявка доходит до `canceled` через
автомат, причина (`resting_add_not_permitted` / `resting_opposite_requires_reduce_only`) едет в
`riskDecisions` с `decisionKind: 'resting'` и событием `order.canceled` в timeline.

`reduceOnly` в эту проверку **не попадает намеренно**: оба её состояния разбирает движок по
знаковому остатку (`reduce_only_flat` / `reduce_only_would_increase`), и вторая проверка того же
вопроса завела бы второго судью, который однажды ответит иначе.

**Flat — не значит «проверять нечего».** Позиции нет, значит ни наращивания, ни пересечения нуля
быть не может, и на этом соблазн остановиться велик. Но потолок экспозиции считается ОТ EQUITY, а
она между подачей и срабатыванием меняется: убыточная сделка её уменьшает. Заявка, принятая при
`E1`, срабатывает при `E2 < E1` со **старым** нотионалом — то есть открывает позицию больше, чем
профиль разрешает сейчас. Поэтому при flat потолок пересчитывается, и вердикт тот же, что у подачи:
accept / clamp (заявка остаётся, но урезанным размером) / reject при исчерпанном потолке.

**Отмена связана с причиной в одной записи.** Идентификатор был у ордера, причина — у вердикта, и ни
одна запись не содержала обоих фактов: связать их можно было лишь сопоставлением двух списков по
номеру frontier'а, то есть догадкой «наверное, отменили именно эту» — она ломается на первом же
frontier'е, где снято больше одной заявки. `ActorCancelReason` — типизированный союз двух
происхождений (движковые причины `executeFill` и риск-контурные `resting_*`); `string` принял бы и
пересказ, и опечатку.

**Кламп проверяется ПРИМЕНЕНИЕМ, а не вердиктом.** Проба, смотрящая на наличие записи «клампнуто»,
проходит и на заявке, вставшей исходным размером: мутация «кламп не применяется к книге» сперва не
покрасила ничего. Сверять нужно нотионал филла.

**Ловушка проб этого раздела:** триггер ждущей заявки обязан быть ДОСТИЖИМЫМ. Первая редакция
временного случая ставила `sell` с триггером ниже ленты, которая только росла, — заявка не
срабатывала никогда, и «ничего не произошло» читалось как «правило соблюдено». Проверять нужно
финальный ledger и отсутствие филла, а не только исходы подачи.

`RiskContext` заполняется так:

- `equity` — `equityOf(ledger, mark, initialEquity)`, функция уже есть в `frontier-runner.ts`;
- `openPositions` — `ledger.qty === 0 ? 0 : 1`;
- `position` — `{ size: |qty|, entryPrice: avgPrice, addCount: ? }`. **`addCount` в
  `ActorEngineState` отсутствует.** Под `DEFAULT_RISK` он не нужен (увеличение запрещено до всякого
  счётчика), но профиль с `dcaLimits` без него неприменим — поле заводится вместе с первым таким
  профилем, а не раньше.

## 4. Applicability matrix — что путь заявляет и чего не заявляет

Обязательная часть контракта среза. Путь **не объявляет полной поддержки** `RiskProfile`; он
объявляет ровно это:

| поле | применяется на actor-пути | где проверяется | если нарушено |
| --- | --- | --- | --- |
| `allowedSides` | **да**, на открытии позиции | `BatchCore.validate` | reject команды, `order.denied` |
| `maxConcurrentPositions` | **да**, при одном акторе | `validate` (в пределах актора) + допуск прогона | reject команды / отказ прогона |
| `exposureLimits.maxPositionNotionalPct` | **да**, клампом нотионала, **только на открытии** | `validate` (reject невозможного) + `apply` (кламп) | заявка встаёт клампнутым размером |
| `dcaLimits` / `scaleInLimits` | **нет** — увеличение запрещено целиком | `validate` | reject любого наращивания |
| `stopBounds` / `takeBounds` | **нет** — носителя нет | — | — |

**Профиль, чьи неприменимые поля объявлены, не делает прогон незаконным** — он делает его частично
покрытым, и это состояние обязано быть названо, а не замолчано. Инвентарный гейт, фиксировавший «ни
одного профиля, все лимиты которого actor-путь соблюдает», развёрнут на 180°: теперь он требует,
чтобы **каждый** зарегистрированный профиль был исполним.

### 4.1 Допуск проверяет совместимость, а не полагается на матрицу (требование владельца)

`DEFAULT_RISK` не навсегда единственный профиль — за ним придут пользовательские. Поэтому
применимость не только записана в этом документе, но и **проверяется в допуске**:

- **whitelist, а не blacklist.** Список исполнимых правил объявлен явно; **любой незнакомый ключ
  профиля отвергает прогон**. Список запрещённого пропустил бы каждое правило, которого мы сегодня
  не предвидели, — то есть ровно те, что появятся позже;
- **проверяются значения, а не только имена, и вложенное наравне с верхним уровнем.** Имя-whitelist
  ловит «правило, которого мы не знаем», но пропускает «знакомое правило с бессмысленным
  значением», а это тот же класс дефекта: `maxPositionNotionalPct: NaN` проходит
  `typeof === 'number'`, после чего каждое сравнение с ним ложно — **потолок молча выключен**, а
  профиль выглядит строгим. Требуется: конечное число > 0 для потолка, целое ≥ 0 для счётчика
  позиций, enum `long`/`short` для сторон, отсутствие незнакомых вложенных ключей
  (`exposureLimits.maxLeverage` не проедет). В самом `evaluateActorPlace` негодное значение —
  **бросок**, а не тихий пропуск проверки: это нарушение инварианта допуска;
- критерий неисполнимости: **у правила есть предмет в actor-языке, но путь его не исполняет**.
  Такое правило — тихое ослабление контроля (пример: `dcaLimits` / `scaleInLimits`, разрешающие
  долив);
- правило без предмета (`stopBounds` / `takeBounds`) прогон не блокирует: ослаблять нечего;
- форма поддержанного правила проверяется отдельно от его наличия: `exposureLimits` без
  `maxPositionNotionalPct` — это объявленный потолок, который не с чем сравнить, и трактовать его
  как «потолка нет» значило бы исполнить прогон свободнее, чем просил профиль.

Отказ — fail-closed, **до создания акторов**, тем же рубежом, что и допуск подписок.

Границы верхнего контура: `riskProfileRef` остаётся привязкой запуска/стратегии. Account/user hard
limits — **отдельный верхний контур**, и гарантии между несколькими стратегиями требуют портфельного
координатора; в S3 его нет и он не подменяется профилем прогона.

Будущее направление, зафиксированное владельцем: **явная bracket/protection-связь в контракте** —
тогда `stopBounds` / `takeBounds` получат носитель, и строка матрицы изменится вместе с версией
контракта, а не втихую.

## 5. Mark-цена: предмета спора не оказалось (уточнено реализацией)

Проектирование закладывало в состояние поле `markPrice` — close последнего **завершённого**
frontier'а — и обосновывало, почему нельзя брать закрытие ТЕКУЩЕГО бара: фазы внутри frontier идут
`execution → timers → market → candle → cascade`, команды на `timer.fired` обрабатываются в фазе 2,
а свеча доставляется в фазе 4, поэтому риск пользовался бы ценой, которой автор ещё не видел.
Рассуждение верное, но **применять его не к чему**.

Потолок экспозиции применяется только при **открытии**, а открытие возможно только из flat:
наращивание запрещено профилем (§8.1), закрытие экспозицию уменьшает. У flat-портфеля
нереализованной части нет по определению, значит `equity = initialEquity + realizedPnl` — **точно**,
а не приближённо. Mark-цена не входит в вердикт ни при каком состоянии.

**Решение изменено:** `markPrice` не заводится. Реализовано `flatEquityOf`, которое проверяет
инвариант (`qty === 0`) и бросает при нарушении. Лукахед исключён не дисциплиной, а отсутствием
входа для него; поле, которое выглядело бы работающей защитой, ничего не защищая, не появилось.

База при этом **не константа**: `realizedPnl` предыдущих сделок в неё входит, и потолок следующего
входа на проигранном счёте ниже. Это отдельный гейт — на ленте без издержек он неотличим от своего
отрицания, поэтому проба гоняется с ненулевой комиссией.

## 6. Место clamp и reject

### 6.1 Reject — в `validate`

Дорога уже построена и используется warm-up-запретом: `{ ok: false, reason }` → `applyBatch`
коммитит префикс, **не применяет** отклонённую, обрывает суффикс, кладёт `order.denied` в outbox,
и раннер пишет исход каждой команды в timeline. Риск-отказ обязан идти этой же дорогой и получить
те же гарантии. Отдельного пути для него нет и быть не должно.

### 6.2 Clamp — в `apply`, и это вынужденно

`Validation` бинарен: он умеет «принять» и «отклонить», но **не умеет «принять изменённое»**.
`applyBatch` передаёт в `apply` ту же команду, что отдавал в `validate`, — подменить её между
вызовами негде. Значит клампнутый размер может появиться только там, где строится
`ActorOpenOrder`, то есть в `apply`.

Три рассмотренных варианта:

| вариант | вердикт |
| --- | --- |
| клампить до `applyBatch` (pre-filter) | **отвергнут.** Ровно то, что запрещено для warm-up: вынимает решение из единственного места, где живёт политика §3.8.4, и делает кламп тихим |
| расширить `Validation` вариантом `{ ok: true, replacement }` | **отвергнут в этом срезе.** Это изменение контракта движка и его bump; предмет S3 — потребитель, а не движок |
| клампить в `apply` | **принят.** Внутри батча, атомарность держится по построению |

Возражение «тогда риск считается дважды — в `validate` и в `apply`» снимается тем, что
`evaluateActorPlace(command, state, profile, initialEquity)` — чистая функция от той же пары
аргументов (команда и состояние), что и обе половины
`BatchCore`. Два вызова дают тождественный результат; это не два источника истины, а одна функция,
вызванная дважды. Кэшировать её между вызовами значило бы завести состояние между `validate` и
`apply` — то самое, чего форма `BatchCore` избегает намеренно.

## 7. Форма `riskDecisions`

**Изобретать нечего: форма уже канонизирована.** `ActorExecutionRecord.riskDecisions` объявлен как
`readonly RiskDecision[]` — движковый тип, — и там же записано, что `barIndex` каждого элемента есть
номер frontier'а. Сейчас раннер отдаёт `riskDecisions: []`; задача среза — **заполнить**
существующий слот, а не завести второй.

Заполнение полей:

- `barIndex` — `state.frontierIndex`;
- `decisionKind` — вид команды (`'place'`); поле объявлено `string`, отдельного словаря не заводим;
- `action` — из `RiskOutcome.action`;
- `reason` — слово риска (`max_concurrent_positions`, `side_not_allowed`, `notional_clamped`, …),
  **не пересказ хоста**;
- `clamped` — `[{ field: 'qtyUsd', from: запрошено, to: применено }]`.

Куда пишется:

- **accept / clamp** — в `apply`, в новое поле `state.riskDecisions` (рядом с `notes`, той же
  природы: единственный наблюдаемый след команды, не оставляющей иного);
- **reject** — `validate` состояние не пишет по контракту. Запись собирает раннер сразу после
  `applyBatch` из `outcome.rejectedIndex` / `outcome.rejectedReason` — в том же месте, где он уже
  строит `timeline` и по тем же данным.

Разнесение по двум местам названо здесь явно, потому что оно неприятно и его легко счесть
недосмотром. Альтернатива — писать всё в раннере — требует, чтобы факт клампа как-то доехал до
него, а доехать он может только через состояние, то есть через `apply`. Круг замыкается: пока
`Validation` бинарен, одного места записи не существует.

## 8. Решения владельца (приняты 2026-08-14)

### 8.1 Долив

**Под `DEFAULT_RISK` запрещается любое увеличение уже открытой позиции.** `dca` и `scale_in` не
различаются и **из косвенных признаков не выводятся**; SDK в этом срезе не расширяется.

Следствие для реализации: различителем служит `intentOf(ledger, side) === 'add'` — то есть знак
позиции против стороны заявки, факт наблюдаемый и не требующий домысла. Причина отказа —
хостовая и одна.

### 8.2 `stopBounds` / `takeBounds`

**Неприменимы к сырой actor-заявке без явной защитной семантики.** Protection **не выводится** ни из
`stop_market`, ни из `avgPrice`. В дизайне фиксируется applicability matrix (§4), и путь **не
заявляет полной поддержки** полей профиля.

Будущее направление — явная bracket/protection-связь в контракте.

### 8.3 `maxConcurrentPositions`

**Single-symbol — применяется нормально.** Multi-symbol под portfolio-wide лимитом — **прогон
отвергается до создания акторов**. **Per-actor трактовка не допускается**: она тихо превратила бы
«1 позиция на портфель» в «до N позиций», и результат выглядел бы законным.

Долгосрочное решение — портфельный координатор над акторами; в S3 его нет.

Следствие для реализации: проверка живёт **в допуске прогона**, где известно число акторов, а не в
`validate`, где сосед невидим. Это тот же fail-closed рубеж, что и допуск подписок: отказ до
`createActor`, с union'ом, у которого полей результата нет.

## 9. Негативные гейты — «без частичных эффектов»

Каждый гейт закрывает состояние, при котором **результат прогона выглядит нормально**:

1. **Отклонённая риском `place` не оставляет ничего.** Ни заявки в `openOrders`, ни
   `order.accepted`, ни записи ордера, ни движения бухгалтерии — только `order.denied` с причиной
   риска и строка в timeline. Проверяется сравнением состояния до и после батча.
2. **Клампнутая заявка стоит клампнутым нотионалом.** В книге — `to`, а не запрошенное `from`; в
   `riskDecisions` — `clamped` с обоими числами. Гейт, сверяющий только факт «есть кламп», прошёл бы
   и на заявке, вставшей запрошенным размером.
3. **Риск-отказ ведёт себя как всякий rejection §3.8.4:** префикс закоммичен, суффикс оборван,
   инстанс жив. Батч `[ok, риск-reject, ok]` обязан дать `committed=1`, `skipped=1`.
4. **Отказ доезжает автору в том же frontier** каскадной фазой, а не на следующем баре.
5. **Увеличение открытой позиции отклоняется** — под `DEFAULT_RISK` это main-line поведение, а не
   край. Отдельно: заявка в ту же сторону при flat — это **открытие**, и она проходит.
6. **Лимит зависит от ТЕКУЩЕЙ equity, а не от стартовой.** Мутация «считать потолок от
   `initialEquity` вместо текущей realized equity» обязана красить именованное утверждение; иначе
   `maxPositionNotionalPct` вырождается в константу, и профиль разрешает набирать прежний объём на
   проигранном счёте. Проверяется в обеих точках — на подаче и при re-валидации ждущей заявки.
7. **`allowedSides` не читается как сторона заявки.** `sell` при длинной позиции обязана
   **проходить** под профилем, разрешающим только long: это выход, а не short. Гейт на профиле
   `LONG_ONLY_RISK`.
8. **Multi-symbol под portfolio-wide лимитом отвергается ДО создания акторов** — счётчик вызовов
   `createActor` пуст. Гейт, проверяющий только терминальный код, прошёл бы и на отказе после
   создания.

9. **Противоположная non-reduceOnly отвергается атомарно** (§3.1): ни заявки, ни филла, ни движения
   ledger; знак и величина экспозиции не тронуты. Различающий случай — та же заявка с `reduceOnly`
   проходит и **действительно** закрывает позицию, а не переворачивает её избыточным размером.
10. **Временной случай:** заявка, поданная при flat, к исполнению встречает позицию. Доказывает
    границу ответственности. Формулировка «риск отвечает за подачу, за исполнение отвечает движок»
    УСТАРЕЛА: с появлением re-валидации (§3.2) момент исполнения принадлежит **host risk
    boundary** — хост проверяет ждущую заявку сам, а движку остаются только состояния reduceOnly
    (`reduce_only_flat` / `reduce_only_would_increase`), которые он различает по знаковому остатку.
11. **Негодное значение профиля бросает** при прямом вызове `evaluateActorPlace`.

Мутационные контроли (каждая обязана покрасить именованное утверждение): снять кламп; заменить
reject на accept; сравнить `place.side` с `allowedSides` напрямую; писать `riskDecisions` только на
accept; пропустить multi-symbol в допуске; считать противоположную non-reduceOnly закрытием;
пропускать non-finite потолок; проверять только имена правил; не смотреть вложенные ключи; снять
re-валидацию ждущей заявки; включить в неё `reduceOnly`; снять заявку, не сняв матч; считать потолок
при flat от СТАРТОВОЙ equity вместо текущей realized; не применять кламп ждущей заявки к книге; не
писать причину отмены в запись заявки.

**Отдельный урок про сами мутации.** Мутация «снять бросок при негодном значении» сперва не красила
**ничего**: гейт совместимости отвергает такой профиль раньше, и до `evaluateActorPlace` он в
прод-сценарии не доходит. Защита инварианта, которую ничто не проверяет, — не защита, а комментарий:
она молча исчезнет при первом рефакторинге. Пробы зовут функцию напрямую.

## 10. Границы среза

Входит: `evaluateActorPlace` и `exposureCeilingOf`, поле `riskDecisions` в состоянии, вызовы в `validate` /
`apply`, отказ multi-symbol в допуске прогона, заполнение `ActorExecutionRecord.riskDecisions`,
перевод `actor-e2e-direct` с самодельного `NO_LIMITS` на `DEFAULT_RISK`, гейты §9, обновление
инвентарного гейта под applicability matrix.

Не входит: sandbox/thread actor lifecycle (отдельный подсрез), `completed` direct/thread parity
(финальный гейт S3), любые изменения `@trdlabs/engine`, расширение SDK, любые bump'ы версий.
